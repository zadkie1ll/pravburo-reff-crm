# Поиск кандидатов Bitrix

`GET /internal/clients/search?q=Иванов%20Иван&page=1`
требует `X-Internal-Token`. Поиск только читает Bitrix; не создаёт лидов,
сделок, привязок или выплат. Он не выбирает клиента автоматически и не меняет
существующий `GET /internal/deals/{deal_id}/existing-client`.

`q`: 3–200 символов, 1–3 слова ФИО, буквы, дефисы и апострофы; пробелы
нормализуются. Пустые/короткие строки, LIKE-шаблоны и неверные страницы — 422.
`page`: целое число 1–1000, по умолчанию 1. Ошибки обязательного поиска,
невалидный ответ Bitrix, превышение лимита связанных сделок или общего
тайм-аута 30 секунд — обезличенный 502 `Bitrix lookup unavailable`.

## Ответ

```json
{
  "rows": [
    {
      "kind": "deal",
      "id": "123",
      "title": "Договор",
      "full_name": "Иванов Иван Иванович",
      "phone": "+79990000000",
      "category_id": 2,
      "category_label": "Сопровождение",
      "stage_code": "C2:NEW",
      "stage_label": "Новая",
      "url": "https://portal.bitrix24.ru/crm/deal/details/123/"
    }
  ],
  "has_more": false,
  "page": 1
}
```

Только эти поля; `id` всегда строка, `full_name` всегда строка,
`phone` — строка или `null`. Для лида `kind="lead"`, `category_id=null`,
`category_label="Лид"`, стадия берётся из `STATUS_ID`, ссылка имеет путь
`/crm/lead/details/{id}/`. Лид — информационный кандидат: для импорта нужно
явно выбрать настоящую сделку. Одинаковые ID сделки и лида — разные кандидаты.

Сделки ограничены `BITRIX_CLIENT_CATEGORY_IDS` (по умолчанию 0 и 2), включая
закрытые стадии: фильтра «только активные» нет. Имена в контактах и лидах
ищутся по первому введённому слову отдельно в `LAST_NAME`, `NAME`, `SECOND_NAME`;
остальные слова проверяются локально как подстроки ФИО без учёта регистра,
в любом порядке. Это не нечёткий поиск: опечатки не исправляются, транслитерация
не выполняется; соответствие е/ё в первичном фильтре зависит от Bitrix.

Для найденных контактов запрашиваются сделки через `crm.deal.list` с
`@CONTACT_ID` и `@CATEGORY_ID`, затем дополнительно через `crm.item.list`
с `entityTypeId=2`, `@contactIds` и `@categoryId`. Второй запрос нужен для
связей с неосновными контактами; его ошибка возвращает 502, чтобы не выдавать
заведомо неполную выдачу как успешную. Состав полей универсального метода
преобразуется из camelCase во внутренний формат. Если совпали несколько
контактов сделки, используется первый совпавший контакт: сначала основной,
затем порядок `contactIds`. Для показа всех кандидатов отдельная строка на
каждый контакт одной сделки не создаётся.

Дополнительно читается страница сделок по первому слову в `TITLE` с локальной
проверкой всех слов, также в любом порядке. Это позволяет найти сделки без
контакта с ФИО в заголовке. Если совпавший контакт отсутствует в текущей
странице, `full_name` берётся из заголовка, `phone=null`: телефон самой сделки
или постороннего контакта не подставляется.

## Страницы и ограничения

Страница поиска **не равна 50 строкам приложения**. Для `page=N` каждый из
семи потоков поиска (три поля контакта, три поля лида, заголовки сделок)
читает одну страницу Bitrix с `start=(N-1)*50` и сортировкой ID ASC.
Связанные сделки текущего набора контактов дочитываются отдельными страницами
с `start=0,50,100,...` до конца обоих методов, не останавливаясь на первой
сделке или первой воронке. Поэтому ответ может содержать больше 50 кандидатов.

`has_more=true` означает, что хотя бы один из семи потоков имеет следующую
страницу согласно `next` или `total`. Если обоих полей нет, полная страница
из 50 записей консервативно означает возможное продолжение. После локальной
проверки слов страница может быть пустой с `has_more=true`; продолжайте с
`page+1`. Нужно просматривать страницы до `has_more=false`, прежде чем считать
поиск завершённым. При `page=1000` и `has_more=true` следует уточнить ФИО:
дальнейшие страницы не разрешены.

На ответ дубликаты удаляются по `(kind,id)`. Между страницами один кандидат
может встретиться снова (несколько полей или контактов); потребитель должен
объединять страницы по этому ключу. Страницы не являются снимком: изменения
Bitrix между запросами могут сместить offset и потребовать повторного поиска.

Каждый из двух запросов связанных сделок ограничен десятью страницами
(до 500 записей на метод). Если после десятой страницы есть продолжение,
весь запрос возвращает 502, а не обрезанный успешный список; уточните ФИО.
Максимум при стандартных двух воронках — 31 read-only вызов Bitrix:
6 страниц имён + 20 страниц связанных сделок + 1 страница заголовков +
1 запрос категорий + до 3 справочников стадий. Нет полного обхода CRM.

Названия воронок берутся из `crm.category.list(entityTypeId=2)`, стадии —
из `crm.status.list` для `DEAL_STAGE`, `DEAL_STAGE_2`, `STATUS`.
Справочники запрашиваются один раз, их собственные продолжения не обходятся;
отсутствие записи или ошибка не скрывают кандидатов. Для всего обогащения
названиями есть отдельный лимит 2 секунды. Резервные названия: 0 — «Основная»,
2 — «Сопровождение», остальные — «Воронка #{id}»; резерв стадии — её код.
Результат ограничен правами чтения владельца настроенного вебхука.

Origin ссылок строится только из scheme и hostname `BITRIX_WEBHOOK_URL`.
Логин, пароль, порт, `/rest/...`, query и fragment исключены. Путь карточки
фиксирован, ID проверяется как положительное число. Сайт может дополнительно
перестроить ссылки из своего настроенного шаблона.
